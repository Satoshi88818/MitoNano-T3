mitonano_orchestrator — T3 Revision, Built and Verified

This is the full crate after the T3 revision: both correctness gaps from the T2 revision are now genuinely fixed (not just documented), plus several of the T3 "Next Steps & Improvements" document's architectural and testing suggestions. Everything below was compiled and tested for real — 61/61 tests pass (55 unit + 3 integration + 3 property-sweep) on a clean cargo clean rebuild, zero warnings, on stock rustc/cargo 1.75.0 (rustc 1.75.0 (82e1608df 2023-12-21)), the version this crate has been validated against throughout T1 → T3.

T2 → T3 changelog

Fixed — T3 doc item 1, "Immediate Correctness Fixes," the two coupled gaps from T2:

DomainDecomposition::ensure_valid_for_halo(min_width_factor) — given a median-cut layout, widens any sub-domain narrower than min_width_factor * halo_thickness by shifting boundaries, distributing the widening proportionally to each sub-domain's original width (T3 doc's Option A). If widening isn't geometrically possible at the requested sub-domain count, falls back to the largest equal-width decomposition that is safe (Option C), rather than installing an invalid one.

OrchestratorCoordinator::rebalance now calls ensure_valid_for_halo on every median-cut layout before applying it. A rebalance can no longer install an unsafely thin sub-domain, full stop.

OrchestratorCoordinator::exchange_boundaries no longer assumes "immediate neighbor" is close enough. It scans outward from each node in both directions and stops only once a neighbor's unexpanded bounds are provably farther than that node's halo distance away. This is correct regardless of any sub-domain's width — it doesn't depend on the rebalance-side fix staying correct forever, unlike the T2 version's documented dependency between the two gaps.

A real, previously-latent bug the T3 property sweep caught and fixed:

DomainDecomposition::domain_containing applied the same half-open (max-exclusive) containment rule to the outer edge of the entire global domain that it correctly applies to internal sub-domain seams. Internal seams need that rule so two adjacent sub-domains never both claim a shared boundary point. But the global edge has no neighbor on the far side to disambiguate against — so a point sitting exactly on it (a real case: an agent that exits the global domain during a step gets clamped there by node.rs) was simply unfindable by any sub-domain, which crashed rebalance the moment such an agent got swept up into a repartition. Fixed by nudging any coordinate that exactly equals the global max inward by a tiny epsilon before the containment lookup; internal seams are untouched, since the nudge only ever fires at the true global edge. This is exactly the kind of bug hand-picked example tests tend to miss and systematic generation tends to find.

Added — T3 doc item 2, "Architectural & API Improvements" (partial):

CoordinatorConfig { imbalance_threshold, rebalance_interval, min_subdomain_width_factor } (T3 doc's suggested field set, verbatim). OrchestratorCoordinator::with_config / .config() / FederatedMitoNano::with_config / .config(). rebalance uses config.min_subdomain_width_factor instead of a hardcoded 2.0. FederatedMitoNano::rebalance_if_needed enforces rebalance_interval as a tick-based cooldown between rebalances.

stats() / ClusterStats (T3 doc's "stats()/metrics()" suggestion): per-node agent counts, per-node ghost-agent counts, cluster totals, and max ghost overlap — cheaper than maybe_rebalance when a caller just wants a snapshot without picking an imbalance threshold.

Added — T3 doc item 4, "Testing & Verification Upgrades" (property testing specifically, partial):

tests/property.rs covers the three properties the T3 document names (agent-count conservation across steps/rebalances, every agent contained by its own node, no ghost-agent duplication) via 200 generated scenarios each. Not actually using proptest — see that file's header for why: proptest's dependency graph pulled in a getrandom release requiring Rust's 2024 edition, which stock rustc 1.75.0 can't parse the manifest for, and pinning versions by hand didn't resolve it either. Substituted a small dependency-free seeded parameter sweep (SplitMix64) with the same testing intent — broad, systematic, reproducible coverage instead of a handful of hand-picked scenarios — with the one honest capability gap being no automatic shrinking on failure.

A real tension the T3 fix surfaces, documented rather than hidden:

Forcing a safe minimum sub-domain width can conflict with count-balance when every agent sits within a span narrower than min_subdomain_width_factor * halo * num_nodes — there's no boundary placement that can give every sub-domain both a fair agent share and a safe width if the agents themselves don't physically span enough room. ensure_valid_for_halo always resolves that conflict in favor of safety (never installs an unsafe sub-domain), which can leave the post-rebalance report still reporting imbalance in that scenario. That's a hard geometric limit, not a bug — see rebalance_can_remain_imbalanced_when_agents_are_clustered_narrower_than_the_safe_minimum_span in lib.rs's tests, which documents it as a test rather than letting it surface as a silent surprise.

Deliberately deferred (T3 document sections 3, 5, 6, and the rest of section 2 and 4 — sampling/incremental rebalance, a distributed-backend trait, dynamic node count, 2D/3D decomposition, checkpointing, fault tolerance, rayon/serde, workspace restructuring, fuzzing, benchmarks): not implemented here. Listed as deferred rather than silently omitted, per the same "what changed, what was reconstructed" discipline the T3 document itself asks for.

//! Axis-aligned bounding box used for both a node's local sub-domain and //! the global simulation domain. //! //! The uploaded source material called `sd.bounds.contains_with_halo(point, sd.halo_thickness)` //! in `domain.rs` — a method that was never defined anywhere in the //! material. This module supplies it for real. use nalgebra::Point3; #[derive(Clone, Copy, Debug, PartialEq)] pub struct Bounds { pub min: [f64; 3], pub max: [f64; 3], } impl Bounds { pub fn new(min: [f64; 3], max: [f64; 3]) -> Self { debug_assert!( min[0] <= max[0] && min[1] <= max[1] && min[2] <= max[2], "Bounds::new requires min <= max on every axis, got min={min:?} max={max:?}" ); Bounds { min, max } } /// Strict containment: `point` is inside `[min, max)` on every axis. /// Half-open (max exclusive) so that two adjoining sub-domains sharing /// a boundary plane never both claim to contain a point sitting /// exactly on it — a real correctness requirement for domain /// decomposition that the source material never addressed at all. pub fn contains(&self, point: Point3<f64>) -> bool { (self.min[0]..self.max[0]).contains(&point.x) && (self.min[1]..self.max[1]).contains(&point.y) && (self.min[2]..self.max[2]).contains(&point.z) } /// Containment against bounds expanded outward by `halo` on every /// axis in every direction — used to decide which sub-domains need a /// given boundary point's data for halo/ghost-region exchange (a /// point near a sub-domain's edge is relevant to that sub-domain's /// neighbor too, not just to whichever domain strictly contains it). pub fn contains_with_halo(&self, point: Point3<f64>, halo: f64) -> bool { (self.min[0] - halo..self.max[0] + halo).contains(&point.x) && (self.min[1] - halo..self.max[1] + halo).contains(&point.y) && (self.min[2] - halo..self.max[2] + halo).contains(&point.z) } /// Clamps `point` to lie within `[min, max]` (inclusive) on every /// axis. //! Property-style tests (T3 "Next Steps" document, section 4: "Testing & //!
